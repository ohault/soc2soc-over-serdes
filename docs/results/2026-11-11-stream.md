Per-second throughput in 7.1: 227.0–227.4 MB/s after the first second (the first second includes
the start, 209 MB/s). With `--throttle=3` it settles at 100.0 MB/s from the second second on.

**Throughput vs. the expected 235 MB/s.** The measured figures follow from the packet format
exactly. A data packet carries up to 64 words, plus 1 stream header word and 2 SerWB framing words
(preamble, port/length): 67 words. The receiver returns a 3-word CREDIT packet every 64 consumed
words, sent on the opposite direction of the same cable:

- one direction streaming: 64 / 67 x 248.1 = 237.0 MB/s, measured 237.0 MB/s;
- both directions of a cable streaming (as in `stream` and `run`): each direction also carries the
  credits of the other one, 64 / (67 + 3) x 248.1 = 226.8 MB/s, measured 226.9–227.1 MB/s.

The README "about 95 %" figure (235 MB/s) matches the one-way case, not the bidirectional test.
Larger packets (`max_packet_words`) and credit batches (`credit_threshold`) would reduce the overhead.

**7.3: register access is not blocked by a stalled stream.** With the consumers almost stopped
(throttle 60000), the RX buffers stay full (463–511 / 512 words) and the TX credits near 0. The
remote identifier, the 256-word mailbox write/read and the direct check pass on both paths (4.7 s,
same as without stream), with no link drop and no RX error.

The stream errors in the "as written" run are caused by the test procedure, not by the stream port:
`test_soc2soc.py remote` first runs the wiring detection, which silences the TX of each SFP in turn
(GTP TX inhibit). Every link goes down and comes back, which truncates the stream frames in flight
(documented behaviour on link loss). The errors all appear within the same second, when `remote`
started, then stay constant. The detection then clears the link drops counters, so `status` showed 0.
Re-running 7.3 with the same remote test on the known paths, without wiring detection, gives 0
errors and 0 frame errors on all four directions for the whole 60 s.

#### Notes

- `./acorn_soc2soc.py --load` regenerates the SoC (`build/sqrl_acorn/csr.csv`, Verilog) before
  loading. Run without `--with-stream`, it writes a `csr.csv` without the stream registers (the
  bitstream itself is unchanged), and `status`/`stream` then do not see the stream port. Load with
  `./acorn_soc2soc.py --with-stream --load --usb-port=...` (section 7 currently says "Load it as in
  2.2").
- `test_soc2soc.py stream` exits with 0 even when errors are counted; only `run` checks the pass
  criteria.
- `--stream-duration=N` counts N one-second sleeps; with the per-second CSR reads over the UART the
  test lasts a few seconds longer. The reported MB/s use the real elapsed time.
- Resource use (placed): 7122 slice LUTs (5.3 %), 22.5 block RAM tiles (6.2 %).
